## Data and sync (what stays on the phone, what goes to Supabase, conflicts, the first-open gate, the erase race, network drops, payload sizes, the Supabase plan, and the live tables)

Everything a guest logs is saved on the phone first and works with no signal; when there is a connection the app sends the whole passport to the server and fetches the crew's, and a dropped connection mid-way leaves nothing half-written, so the everyday offline behaviour is sound. The big gap is recovery: every guest is anonymous, Google sign-in is still blocked on Charles's Google account, and the server's private backup is only ever read back for a signed-in user, so a lost phone or cleared Safari data loses that passport and its friend code for good. The live database is almost all test data: of 156 shared passports, 125 are exactly the demo seed, only 2 hold real non-demo drinks, there are 2 friend links and no groups at all, so the family features have barely been used for real. The demo link in the public README switches sync on without the consent screen, which is how most of that test data got there, and it leaves dozens of look-alike profiles that the name search will show the family. The known race between Delete my data and a sync already running is real: it can re-create the deleted rows, or create a new anonymous user holding the old name, and it breaks the privacy note's promise, but it needs an unlucky moment, so it should be fixed rather than hold up the launch. Two more code paths matter on patchy ship Wi-Fi: requests have no timeout, so one stalled call can leave the app saying 'Syncing…' until the request finally fails, and a rejected token refresh would quietly give the phone a new identity whose next sync empties the crew list (I traced this in code; it has not happened live). The Supabase project is small and nowhere near its limits, but it pauses after seven idle days, and nothing is set up to keep it awake or to warn anyone if it stops. Before sailing, Charles needs to switch sign-in on and test a restore on a family phone, clear out the test profiles, and add a daily check that keeps the project awake and alerts him if it goes down.

## Offline and the PWA (service worker, what works with no signal, the update flow, iOS Safari storage and install)

The app is live and, once it has been opened with a signal, the whole thing works with no signal: every screen, all 214 drinks, logging, ratings, the shaker, badges and Wrapped are downloaded to the phone on the first visit (about 540 KB over the wire). What needs a connection is only the crew side: finding people by name, pulling friends' latest drinks, and joining a group, and a group join tapped offline is saved and done later. The big risk is how iPhones store things. A passport kept in a Safari tab and one kept in the home-screen app are two separate passports, and nothing on the phone tells a guest to add it to the home screen before they start logging. So a guest who logs a few days in Safari and then installs it opens an empty passport, and they have no way back because nobody can sign in with Google yet. The same split means a friend's invite link, which iOS always opens in Safari, adds the friend to the wrong copy. I also found, by reading the sign-in library's code but not by testing it, a likely fault on ship Wi-Fi: open the app with no signal, connect within a minute, and the app can quietly become a new user. That user's crew list is then wiped and syncing stays stuck for the rest of the cruise. Nobody has checked offline use on a real iPhone, and that check is still open on the project's own list.

### Missed by the reader

- Error classification in auth-js (lib/fetch.js:35-49). A refresh answered with a non-JSON response whose status is not 5xx, such as an HTML 4xx, 429 or 511, becomes AuthUnknownError. That error is non-retryable, so once the token has expired _removeSession deletes the session outright and the next ensureSession mints a new user, with no 60 s window needed. A Supabase 429 is JSON and ends in the same removal. For an HTTPS host a captive portal usually cannot answer at all, so fetch throws and the error is retryable (fetch.js:125-130). What the ship's portal actually does is untested.
- Wrapped already produces a keepsake PNG through the share sheet or a download (Wrapped.tsx:85-119 on main). The gap is an export of the passport data, not a Wrapped image.
- The desktop landing's QR code opens / in the phone's Safari, where a cold phone gets Entry. /get on a cold phone also gets Entry, because App.tsx:194 needs isDesktopVisitor and :200 has no path test. So no guest on a phone ever sees the install steps before they start logging.
